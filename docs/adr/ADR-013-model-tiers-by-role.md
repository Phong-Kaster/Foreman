# Model choice is tiered by role, assigned at arm's length, and named abstractly

Different roles in a run warrant different model capability. A Worker implementing a narrowly-scoped, mechanically-specified task (per its Declared File Scope) does not need the same model as the Reviewer challenging it, the Verifier certifying completion, or the Orchestrator that plans, wires shared files, and reconciles. Two rules govern this:

1. **Tier is assigned by role, and for Workers, by task classification done at arm's length.** The Reviewer, the Verifier, and the Orchestrator (the top-level Iteration itself, in every capacity including acting as Verifier) always run at the **Capable** tier — their job is exactly the judgment-heavy work that tier exists for. A Worker's tier is decided once, at planning time, by the same fan-out analysis roles that already produce the task decomposition and conflict analysis (ADR-009) — never by the Worker itself, and never by the context that will implement the task. This is the same discipline as ADR-005 (a context does not certify its own work) extended to planning.
2. **The specification speaks only in tier names, never vendor model identifiers.** `ENGINE.md` and `POLICIES.md` say "Fast tier" and "Capable tier" and nothing more specific. The concrete mapping from a tier name to an actual model identifier lives in exactly one place: `.harness/loop/models.json`, a small adapter-owned file the engine reads but can never write (covered by the existing `.harness/loop/**` deny rule). Porting to another engine means editing this one file; the specification does not change.

## Considered Options

- **Let the engine judge a task's complexity at dispatch time and pick a model itself** — rejected: this is self-assessment bias, the same failure mode ADR-005 exists to prevent. A task that reads as simple in the PRD can hide real subtlety; the context about to implement it is the least reliable judge of that.
- **Hardcode a model name in each `.harness/loop/agents/*.md` file's frontmatter** — rejected. It works technically (verified: the frontmatter's `model:` field is accepted), but it re-introduces exactly the vendor coupling ADR-006 confines to the adapter boundary, spread across every agent definition instead of confined to one file. The dispatch-time override (verified: the Agent tool's own `model` parameter takes precedence over frontmatter) is the right lever precisely because it is supplied by the orchestrator at the moment of dispatch, informed by data read from the Model Tier Map — not baked into a static file.
- **Downgrade the Reviewer or Verifier to save cost** — rejected outright. These roles exist to catch what a Worker got wrong; downgrading the checker alongside the doer erodes the one property this architecture protects. Cost optimization applies only to the Worker's implementation step.
- **Classify tier per-Phase or globally for the whole run** — rejected in favor of per-task: a Phase can mix a trivial task with a complex one, and the Declared File Scope already gives per-task granularity for free.
- **Let a downgraded Worker retry at the same tier on failure** — rejected. A failed attempt is itself evidence the task was misclassified, misunderstood, or simply hard; the second attempt should not repeat the same mistake with the same capability. Escalating to Capable tier on any Fast-tier failure is mechanical, costs nothing extra (no additional attempt consumed), and mirrors the general principle used throughout this design: when a failure mode is ambiguous, resolve it toward the safer, more capable outcome.

## Consequences

- **Task Model Tier criteria** are objective and mechanically checkable (recorded in `POLICIES.md`, a tunable, not a specification invariant): Fast tier requires a bounded Declared File Scope with no shared/integration files, acceptance criteria that are exactly checkable (a literal output, an exit code, an existing pattern to follow) rather than open-ended judgment calls, and no embedded architecture decision or new dependency. Everything else defaults to Capable.
- The critique role from ADR-009 additionally sanity-checks tier assignments, not only the decomposition itself — a task misclassified as simple by the same role that proposed it would defeat the arm's-length principle.
- `.harness/loop/models.json` ships with sane Claude Code defaults (`fast`, `capable`) and is human-editable at install or port time; it carries no authorization semantics, so it needs no ledger/approval machinery — it is configuration, not a capability.
- Reading it needs no new permission: the baseline ledger already grants `Read(**)`, and the existing `Edit(.harness/loop/**)` / `Write(.harness/loop/**)` deny rules already cover it — no `run.ps1` change was needed for enforcement.
- Joins ADR-006's list of adapter-boundary surfaces: the Model Tier Map, alongside event-stream parsing and permission compilation, is where vendor-specific naming is deliberately allowed to live so the specification above it does not have to know it exists.
